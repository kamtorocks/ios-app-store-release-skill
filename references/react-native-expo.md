## One source of truth for native config

- Expo with Continuous Native Generation (`ios/` gitignored, generated by `npx expo prebuild` or by EAS Build) takes all native settings from `app.json` / `app.config.js` and config plugins.
- If `ios/` is committed, EAS Build uses that native project as-is, and native fields in app config (`ios.infoPlist`, `ios.entitlements`, `ios.config`, plugin settings) are not applied. Edits in app.json then silently do nothing. Choose one model per project and state it in the README.
- React Native without Expo: the Xcode project is the source of truth, and everything in the native-Swift rules applies directly.

## Info.plist, entitlements, privacy manifest, export compliance

Expo app config keys:
- `ios.infoPlist`: purpose strings and other Info.plist keys.
- `ios.config.usesNonExemptEncryption: false`: writes `ITSAppUsesNonExemptEncryption = NO`, so builds stop showing "Missing Compliance".
- `ios.entitlements`: extra entitlements. Capabilities such as Sign in with Apple are usually enabled through their module's config plugin or `ios.usesAppleSignIn`.
- `ios.privacyManifests`: the app-level `PrivacyInfo.xcprivacy` (required-reason APIs, collected data).

Purpose strings:
- Config plugins of modules (camera, location, media library, contacts...) insert a default purpose string when you give none. Defaults are generic ("Allow $(PRODUCT_NAME) to access your camera"), and reviewers reject strings that don't say what the feature does (5.1.1). Pass a specific string through each plugin's options.
- The capability-symmetry rule applies here too: a module's plugin can add a key for a feature that isn't in this build.

## Native modules are linked whether or not JS calls them

Autolinking links every native module in `package.json` into the binary. A screen hidden in JS still ships the module's frameworks, purpose-string requirements (ITMS-90683) and visible capability (for example CoreBluetooth from a BLE library, which can draw a hardware demo-video request under 2.1).

To keep a module out of a store build:
- React Native CLI autolinking: `react-native.config.js` can disable a dependency on iOS (`dependencies: { 'pkg': { platforms: { ios: null } } }`). It is JavaScript, so it can switch on an environment variable that the store build doesn't set.
- Expo modules: `expo.autolinking.exclude` in `package.json`.
- Then guard the JS import so the excluded module is never required at runtime. Confirm with `inspect_ipa.py` that the framework is gone.

## Variants (flavors) and build-time environment

- Use `app.config.js` that reads an environment variable (for example `APP_VARIANT`) set per profile in `eas.json`, and derives the bundle ID, name, icon, plugins and `infoPlist` from it. Each variant gets its own bundle ID and App Store Connect record; see "Flavors" in build-and-upload.md.
- Environment values are baked into the JS bundle at build time (EAS `env`, `.env` via babel plugins or react-native-config). A dev value present when the release bundle is built ships to review, the same leak class as Flutter's Generated.xcconfig. Build store binaries only from the store profile on CI or a clean checkout.

## Version and build numbers

- `expo.version` becomes `CFBundleShortVersionString`, and `ios.buildNumber` becomes `CFBundleVersion`.
- With `cli.appVersionSource: "remote"` in `eas.json` and `autoIncrement: true` on the production profile, EAS stores and increments the build number. That is the Expo equivalent of `manageAppVersionAndBuildNumber`: set the marketing version, never hand-pick build numbers.
- React Native CLI: same as native. Set `MARKETING_VERSION` and let Xcode export manage the build number.

## Over-the-air updates

EAS Update and CodePush replace JS and assets only. Info.plist, entitlements, purpose strings, native modules and privacy manifests change only with a new binary and a new review. Updates must not introduce or change features beyond what was reviewed (2.5.2: apps "may not download, install, or execute code which introduces or changes features or functionality"). Keep OTA for fixes and content, and make sure updates are compatible with the binary's runtime version.

## Sign in with Apple

- `expo-apple-authentication`'s `AppleAuthenticationButton` renders Apple's native button, which complies with the HIG. Don't replace it with a custom-drawn one.
- `signInAsync` returns `fullName` and `email` only on the first authorization. Persist them immediately (4.0: never ask again).
- For token revocation on account deletion (5.1.1(v)), send the returned `authorizationCode` to your server, exchange it at `/auth/token` for a refresh token, and store it. For native sign-in, the `client_id` is the app's bundle ID, not a web Services ID. See rejection-playbook.md, 5.1.1(v).
- Google or other social login for the primary account requires an equivalent private option (4.8); Sign in with Apple qualifies.

## Build and submit

- `eas build -p ios --profile production`, then `eas submit -p ios` (or `--auto-submit`). EAS uses an App Store Connect API key it manages, or one you provide.
- `eas build` uploads only the binary. Review Notes, the demo account, App Privacy answers and screenshots are still set in App Store Connect; use submission-checklist.md.
- Apply the same reviewer-path tests: release build, fresh install, sandbox purchases against the production backend (iap-subscriptions.md).
